# 报告要让读者能判断该不该修

## 读者与目的

issue 的读者是维护者，他要判断两件事：这算不算缺陷，修在哪一层。正文只服务这两件事。

## 骨架

1. 一句话说出现象与后果：什么操作，得到什么，为什么不对。
2. 错误流程图：从触发点画到调用方看到的结果，在出错的那一步标出丢失或错置。
3. 位置表：仓库、模块、行号，一行一处。位置是读到的事实。
4. 修复流程图：从断点画到期望结果，标出改动落在哪几层。
5. 期望：可判的读数，例如某个字段取某个值。
6. 未决问题：单独列。

## 判据

- 读者只看正文，能否说出错在哪一步、修在哪几层。说不出就缺图或缺位置。
- 删掉任意一段后，读者是否仍知道现状、理由、代价。知道就删。
- 每条位置能否在代码里点开。点不开的降为未决问题。
- 每个复现步骤是否真跑通过。没跑通的降为触发条件加观察到的现象。
- 期望是否落在字段、状态或返回值上，而不是「正常工作」。
- 正文是否出现核实过程、判断反复、当前实现的正确流程。出现即删。

## 先草稿

改线上正文前先给草稿，等确认再写。直接改会把未定的判断写成既成事实。

## 功能请求

写当前状态与目标状态之间的差距。实现步骤留给方案评审，除非读者要靠它判断可行性。
