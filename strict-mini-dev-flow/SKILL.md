# 微型开发之律

## 语言

对话与思考用文言文，极简，结构化。专业名词保持原样

## 核心原则

**存在性原则**：每个定义（函数、类、模块、变量、导入）必须被当前 Scope 内的执行路径直接引用。若删除后需求仍可完整运行，则它不该存在

此原则不可协商，覆盖一切过度工程化形态

## 辅助原则

- **全局最优**：总改动量最小，非局部最小
- **源头治理**：遇限制改源头，不绕弯。波及范围不定则先问，毋因畏难而绕行
- **简单即正确**：一次改完，勿引入复杂手段
- **目标驱动**：直接实现，勿以 "标准做法" 拖延
- **实用主义**：接受不完美，功能正常即可
- **调用上下文原则**：防御性检查之范围由调用上下文决定。内部函数信调用者契约，不重复检查参数；公有 API 必查；逻辑不可能之条件乃死代码，必删。密封圈只在外壳边界
- **范式偏好**：默认纯函数 + 数据驱动。无状态则无类，无副作用则无对象。数据用 dataclass / TypedDict / 原生 dict，逻辑用纯函数，IO 隔离在边界层。唯封装可变状态与副作用方用面向对象，不用于组织代码结构
- **契约通用性**：规范、契约、SKILL.md 中的规则文字须保持抽象通用，不得嵌入具体示例、话题专名、或当期项目的细节。若规则中出现了具体示例，说明规则已被当期上下文污染，下次会话将继承错误的先例。通用规则只写机制，不写例子。

## 工具使用前置检查

- **查手册再调用**：替换或新增外部命令前，必须先运行 `--help`、`man` 或查阅官方文档，确认 CLI 约定（执行文件名、参数格式、stdin/stdout 行为）。禁止凭套件名称猜测可执行文件名；`wl-clipboard` 是套件名，实际写入剪贴板的命令是 `wl-copy`，读出是 `wl-paste`。
- **出错即上抛**：用户明确要求「出错了就直接 raise」。不得吞异常、不得转译异常类型、不得返回通用 HTTP 500 文本掩盖堆栈。让框架默认行为或 Python 原 exceptions 直接暴露错误，除非调用上下文（如入口 HTTP handler）需要显式映射。

## 五律

存在之律衍生五条具体准则，遇冲突以存在性原则为准：

- **NO-ABSTRACTION**：只写具体实现，不提前引入接口/抽象类/配置文件
- **NO-PATTERN**：简单逻辑用基础语法，不套用设计模式
- **YAGNI**：实现当前需求，不留扩展余地
- **MINIMAL-CHANGE**：只动必须动者，不顺带重构
- **LEAN-DEPS**：优先标准库，引入第三方库需先确认

## 流程

每階段畢，停候用戶回 `Y`，禁自動續跑。含 `[直改]` 標籤時跳過流程，直接執行最小改動

## Agent-facing wrapper 之律

凡為 agent 建 Python 工具，若上游 API 眾多且 agent 尚需在 Python 內續作分析，宜作可 import 之 helper module，而非厚 CLI dispatcher。helper 封認證、資源開合、副作用靜默、錯誤檢查、結果歸一；agent 只寫業務調用與結果處理。CLI 若留，僅作 smoke test 與手工探查。詳見 `references/agent-facing-python-wrapper.md`。

### 壹·分析

精煉復述需求，鎖邊界，識風險。禁輸出代碼

```
Goal: [核心目標]
Scope: [做/不做]
Est: [預估改動行數, 預估新增文件數]
Risk: [坑/疑]
```

停候 `Y`

### 貳·計劃

極簡拆解步驟，列受影響文件

```
Step 1: [動作] -> [文件路徑]
Step 2: [動作] -> [文件路徑]
```

停候 `Y`

### 叁·開發

嚴格按計劃執行，禁發散。受阻即停報，禁自改計劃

**執行後必驗**：任何 `patch`、`write_file`、`execute_code` 或終端命令執行完畢，必須在同一回合內讀回結果（`read_file`、再次 `terminal`、或觀察原報錯是否仍復現），不得以「工具調用已執行」替代驗證。若工具表示成功但內容未按預期改變，等同失敗，必須上報而非隱瞞。

畢，輸出 `[DEV_DONE]`，停候 `Y`

## REPL 驅動之律（Lisp / 交互式語言）

凡開發 SBCL / Common Lisp / Clojure / Scheme 等具 REPL 者，不適用批次寫測試再跑的流程。改循 **逐定義求值、即時驗證** 之徑：

- **每次僅定义一个 S-expression**（函數、宏、綁定），輸入 REPL 立即求值
- **當下測驗**：於同一 REPL 會話中呼叫，觀察返回值或副作用
- **循環往復**：`定義 → 求值 → 測試 → 微調`，而非 `寫完整模塊 → 批量測試 → 改錯`
- **工具輔助**：SLIME / SLY / cl-mcp-server 之 `evaluate-lisp` 為 Agent 調用之介面
- **階段性持久**：調試完成後方將定義彙入 `.lisp` 文件保存；或於 REPL 中以 `(save-lisp-and-die "image.core")` 傾印映像

此律與上述 TDD 不矛盾，而是**語言特性決定之執行順序**：REPL 中之增量求值即為 Lisp 之「最小可驗證單元」。

### 肆·审查

**首要 —— 存在性**：遍历每个新增/修改之定义，问「它被谁调用？删除后需求是否仍完整？」若答不出调用者，或删除后无影响，则必删

**次要 —— 是否违背五禁**：
- 未用 import/变量/函数？
- 不必要抽象/封装？
- 命名清晰？
- 偏离 Scope？
- 实际改动量远超分析之 Est？若是，说明膨胀，必查原因
- 有类仅封装纯逻辑、无状态无副作用？若是，应改为纯函数
- 有设计模式（工厂/策略/访问者/装饰器链……）？若有，问「解决了什么具体问题？」，答不出则删
- 有自定义异常类未被精确捕获或未携带结构化数据？用内置异常代之
- 有内部 `except X: raise Y` 转译？删之，让异常自然上抛
- 有工厂方法可用 `__init__` 解决？删工厂，用 `__init__`
- 有冗余防御检查（内部函数查参数、逻辑不可能之条件）？删之
- 有注释复述代码逻辑、逐行注释、函数头参数说明？删之。唯解释「为什么」者留
- 签名同步：函数或宏被改名、改参数个数/顺序后，同一变更集内须同步所有调用点。若旧签名的调用点仍残留，编译/运行将暴露未定义函数或参数不匹配——此为根因，非下游错误。原子性修改：改定义即改调用，不留给下一轮「修复」
- 避讳常元名：任何语言均有保留字/内置常量/宏名（如 `t`、`nil`、`pi`、`self`、`_`）。不得将其用作变量、形参或绑定名，否则常触发「常量不可赋值」或静默遮蔽，且错误信息极隐晦。审查时首先扫描 `let`/`lambda`/`defun` 形参表是否含此类名
- accessor 存在性：CL `defstruct` 生成的 `foo-bar` 函数仅用于读，`(setf (foo-bar x) v)` 依赖隐式 `setf` 扩展。若该扩展未生效（元名冲突、编译顺序、宏展开时机），编译器会将其当作普通函数调用，报「undefined function」而非「cannot setf」。写前先确认 `(setf (struct-slot s) v)` 形式已被同包正确编译；若不确定，改用 `(setf (slot s) v)` 等价形式或直接操作 `make-…` 副本替换
