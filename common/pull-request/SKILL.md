# PR 交付

平台命令见 `github-pull-request` 与 `gitee`，本文只写两个平台都成立的部分。

## 目标与通路分开判

交付目标由仓库关系决定，推送通路由权限决定。有写权限不证明该仓库就是交付目标。

先判目标：仓库是 fork 时交付目标是父仓库，base 取父仓库默认分支，head 写 `<你的账号>:<branch>`；不是 fork 时目标是本仓库。remote 名与权限都不参与这条判断。

再判通路：在交付目标仓库上查当前身份的角色。可写直接推；只读不可推。

不要用 `git push` 试权限：拒绝只是最省事的结果，成功会改写远端。凭据属于个人账号而仓库属于组织时直接说明，不反复试。

## 归属先判

仓库 owner 与当前账号不同即不是你的仓库，一律 fork 后推 fork、向父仓库开 PR。权限不改变这条：有 WRITE 也不直接推别人的仓库。本地克隆放 `~/code/<repo>`。

## 分支先于 PR

PR 要求 head 分支已在远端存在。报 head 为空、无提交、head 不是分支时，先核推送是否真的成功，不要当作 PR 参数错误去改参数。

改 PR 前先核远端 head 是否已是这次的提交。本地提交没推上去时 PR 上仍是旧提交，改正文掩盖不了这一点。

## 两条通路分开验证

SSH 与 HTTPS 是独立通路，一条不通不证明另一条不通。经代理转发时在握手阶段超时的是网络，不是权限。

退出码要显式取：`cmd | tail; echo ${PIPESTATUS[0]}`。管道后的 `$?` 是 tail 的。

## 正文体例

正文写两件事：改了什么，为什么这么改。

正文里的流程用 mermaid 图表示，不写成大段散文或逐步罗列。

检查输出与运行记录不进正文，随失败贴评论。

正文只写当前状态，不写沿革。

## 次序

查身份 → 判交付目标 → 在目标上查权限 → 推分支 → 建 PR → 复核 base 与 head → 回 URL。任一步失败即停，把报错原文交出去。
