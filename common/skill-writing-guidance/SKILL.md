# 技能文件的写法

## 总则

SKILL.md 是调用契约，不是系统文档。它只回答三个问题：何时触发、怎么调、结果在哪。内部如何实现，读者读完代码自明，不在此复述。

## 触发只写进 description

- `description` 同时承载本质与触发条件，写作「一句是什么。何时用时用。」缺后半句，读者无从判断是否加载；缺前半句，读者不知这份技能管什么。
- 正文不提触发条件与适用场景，也不以「何时加载」之类标题开头。
- 正文一级标题不与 frontmatter 的 `name` 相同，要体现这份技能的定位，而不是重名。

## 正文与契约分开

| 层 | 写什么 | 读者 |
| --- | --- | --- |
| SKILL.md | 何时触发、加载哪些文件、参数、执行注意 | 决定是否加载的人 |
| 契约文件（技能另有者） | 产出什么、质量如何、路径在哪 | 已加载并执行的人 |

- 输出质量、格式、命名、路径等规范，没有契约文件承载时，必须写进 SKILL.md 正文。放进 references 的规范，读者跳过就失去约束。
- 技能另有契约文件时，SKILL.md 只指向、不复制。复制会让同一规则存在两处，改一处漏一处，读者也不知该听哪一份。
- 一条规则只存一处。同一规则出现第二份，删掉其中一份。

## 一处一责

- 一份技能只覆盖一类场景。通用规则写进通用技能，特定场景各建独立技能。
- 往通用技能里加条目前，先问「这条是否约束一切会话」。答否，就建专用技能以限制加载范围。
- 判断某条是否放错了地方，用两个测试：把它的适用主语换成某个特定场景，若语境依然成立，这条属于那个场景；或问「删掉这条，通用技能是否仍然自洽」，答是，则它是外来的插入。

## 迁移即泛化

跨文件迁移内容时，在同一轮里把具体案例名换成通用概念，不要先迁移、再等被指出才泛化。

具体案例名是谜面，它属于被验证的上下文，不是可复用的规则。目标文件的读者没有原案例的上下文，留着名字会让他以为这条规则只适用于那个案例。

把 references 的内容迁进契约时，做语义编辑，不整段复制：提炼行为约束的本质，去掉案例上下文。

已整合进契约的 references 文件删掉。只有尚未整合、或独立有价值的参考才留。流程图一类辅助理解的东西属文档，放进 `docs/`。

## 文风

- 写完整的句子，每句有主语和谓语。
- 立判据，不列细目；示例只给到能看懂的那一行。
- 同一个事实只说一处。

## 自建技能的归属

用户手写的技能放进 `~/code/agent-skills/` 的三棵树之一，判据见仓库 README，由外部目录加载。不要直接写进 harness 自己管的技能目录，那里会被它的更新命令覆写。来源不是用户手写的技能不可迁移。

放错了位置，用整目录 `mv` 迁移，不要 `rm` 后重写。

## 写完核对

逐条问：这条必要吗？是不是在重复别处？示例里还有没有案例名？读者只看这份文件能不能照着做？
