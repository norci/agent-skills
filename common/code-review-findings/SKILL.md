# 评审一条改动

## 规格从哪来

行为与测试是规格。注释、docstring 与行为不符时，改注释；不据注释改行为，也不据注释推出用户没提的需求。

## 发现的写法

每条发现按「不变量 → 所属层 → 唯一完成路径」写：这次改动必须始终成立的事实，拥有它的那一层，以及该层唯一能走完的改法。级别只标严重性，不替完成路径。

指不出改哪一层、哪一处的，不是发现，删掉。

## 动文件之前

评审只交发现。用户说 edit、implement、fix 之后才动文件。代码里的「不一致」「可以更简单」不构成需求，只报给用户。

## 判据

- 先跑守门看基线：红项区分「本次改动引入」与「仓里本来就红」，后者不记在这条改动账上。
- 每条发现指到符号与行；指不到的标「未核」，不写成事实。
- 报出的改动面与实测 diff 对得上：说了改几处，diff 里就是几处。
