# 架构重构技能

## 何时使用
- 用户要求重构代码、重新设计架构、拆分模块、消除技术债、提升可扩展性。
- 任务涉及跨模块、跨层级的结构性变更，而非简单修 bug 或加功能。

## 定位（先读）
1. **遗留代码是被替换对象，不是约束。** 它的内部结构、坏接口、已知缺陷都不构成新架构绕行的理由。要保留的对外行为以「行为基线」为准，未点名的一律不保留。
2. **目标架构经用户确认后即契约。** 实施中发现某步按目标架构走不通 → 停下，改设计，重新确认。禁止就地变形：把新架构塞进旧结构、加分支绕开旧代码、写 shim 透传。
3. **diff 大小不是判据，删完才算完。** 判据只有一条：每步朝目标架构收敛，旧结构删除完成才算任务完成。全局「最小改动」纪律约束的是单 commit 不夹带无关改动，不是重构方案选保守。

## 设计原则（目标架构的判据）

模块化是目标，高内聚低耦合是判据，层次化是结构约束。以下每条都带可检验判据；哪条满足不了，就写进方案「必要取舍」并给原因，不许含糊带过。

1. **高内聚**：一个模块只因一个变化原因而改。判据：取三类典型新需求推演，理想情况各只落在一个模块；每个需求都要横跨多个模块 → 边界切错，重切。
2. **低耦合**：模块间只经接口通信，互不知对方内部。判据：改模块 A 的内部实现（不动其接口），其余模块应零改动、零重测。共享可变状态、直读对方内部结构、隐式约定（魔法参数、约定路径、调用时序）都按耦合计。
3. **层次化、单向依赖**：模块分层（策略 → 领域逻辑 → 机制 → IO），只许上层调下层，禁止下层回调上层、禁止循环依赖。判据：依赖图是 DAG，画不出环。
4. **稳定者居中，易变者靠边**：核心逻辑不依赖框架、IO、配置格式等易变外围；易变点收进扩展点，新需求以「新增一个实现」满足。判据：加一类新外部依赖或新策略，核心代码零 diff。
5. **接口窄而完备**：对外暴露的类型与函数取最少，但覆盖模块全部职责。接口不得泄露内部表示：返回内部数据结构、要求调用方按内部顺序调用、参数里夹内部标志位，都算泄露。
6. **可替换依赖从外注入**：时钟、随机、存储、外部服务等能力由调用方传入，不在模块内写死；写死则无法单测、无法换实现。

## 工作流程
接到任务后先输出方案，经确认再实施：

1. **现状诊断**：模块边界与职责、依赖方向、数据流与状态归属、关键不变量、根因问题；**列出遗留缺陷清单**（默认不迁移、不复刻）。
2. **目标架构**：模块 / 职责 / 接口、依赖方向、扩展点、必要取舍。设计逐条对照上方设计原则。
3. **差距分析**：现状到目标的主要差距；继续局部修补如何恶化。
4. **行为基线**：列出须逐位保留的对外行为（用户点名或现有测试覆盖的对外契约）。bug 行为不在基线内；用户明确要求「行为不变」型重构时除外（逐位对拍）。
5. **迁移计划**，默认策略 = 先立新、再搬迁、后删旧：
   - 新模块 / 接口先立骨架，可独立测试；
   - 调用点逐个迁到新结构，每步可编译、可测试、可回滚；
   - 最后删除旧结构；删除完成前不得宣告完成。
   - **兼容层默认不写。** 要写须出示理由（如外部消费方无法同步迁移）+ 删除时机，经用户确认。
6. **验证标准**：测试、类型、契约、行为 / 性能不变量。

## 实施纪律
- 每想「先不动旧代码」「加个特判绕过去」「写个转发函数保住旧调用点」→ 这就是在塞架构，停下回到目标架构。
- 妥协只许落在外围（脚本、日志、一次性工具），不许落在模块边界、依赖方向、核心接口；须出示具体证据（文件 : 行 + 什么约束），不许用「风险大」泛指。
- 每阶段一 commit，阶段名对齐迁移计划。

## 自查（每阶段结束数一遍）
- 新代码对旧模块 / 旧函数 / 旧字段的引用数 > 0 → 未收敛，继续迁。
- 为少动旧代码而生的分支、shim、透传、复制 > 0 → 违纪，回退该改动。
- 对照缺陷清单：遗留缺陷是否被新代码复刻。
- 对照设计原则：循环依赖、跨层引用、共享可变状态、泄露内部表示的接口，任一出现 → 停下回改设计。

## 禁止行为
- 以最小 diff 为目标，或以「改动小」为方案辩护
- 用 if/else、复制粘贴、特殊分支、shim 绕过新抽象
- 只改调用点却保留坏接口
- 默认写兼容层；无迁移计划就局部打补丁
- 实施中擅自偏离已确认的目标架构

## 输出格式
先输出：
现状诊断 → 目标架构 → 差距 → 行为基线 → 迁移步骤 → 验证方式 → 风险
方案末尾只问上文未定死之开放点（行为基线自用户点名与现有测试覆盖导出、兼容层默认不写 —— 二者已由定位与默认策略定死，不再问）。经确认后再实施。
