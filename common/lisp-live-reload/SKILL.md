# 源码与镜像的回路

镜像里的结论只回答缺陷落在哪一层，不回答改对了没有。判绿由干净进程给出。

## 载入会阻塞会话

载入是同步阻塞操作。`asdf:load-system` 在镜像里重编译并载入整个系统，几十秒到几分钟，这段时间会话停在那次 tool call 上，超时后转成后台作业，读数要等下一轮。

判据本来就在干净进程里重编译全部源码，镜像里再载入一遍对判据没有增量。所以：

- 需要整个系统重载的情形（宏、内联声明、泛型签名、包导出）不在镜像里做，直接去干净进程。
- 只为定位层载入时，只载入本轮改过的单个文件，不载入系统。
- 载入放进后台作业或干净进程，不夹在一条要立刻返回读数的链里。
- 载入失败与判据失败分开报：前者说明源码没读通，后者说明行为不对。

## 回路

1. 改源码文件。
2. 需要定位层时，只载入本轮改过的文件，必要时连同它们的调用者；源码里删掉的定义要手工撤掉（见下）。不需要定位层时跳过这一步，直接第 5 步。
3. 在镜像里构造输入，跑目标行为，读结果。
4. 失败回第 1 步。
5. 通过则在干净进程里载入系统，跑对应套件。
6. 提交前在干净进程里跑完整检查。

第 3 步负责定位，第 5、6 步负责判据。

## 载入范围

载入一条定义不会重编译已经编译过的调用者，范围按改动落在哪一层定。

| 改动 | 载入范围 |
| --- | --- |
| 函数体、方法、可重载参数 | 该文件 |
| 宏、内联声明、类型声明 | 该文件与它的调用者 |
| 类定义 | 该文件；持久对象从磁盘重读后再验 |
| 泛型签名、包导出 | 干净进程里整个系统重载 |

判据是一个问题：这个符号的调用者是否需要一起重编译。宏与内联答是，函数体答否。

## 定义落在文件指定的包里

判据：载入文件后，符号在文件 `in-package` 指定的包里找。

做法：测试调用带包限定，或先把 `*package*` 绑到那个包再求值；`load` 返回 T 不代表定义在调用者的包里。

## 值得进镜像的改动

长期存活的状态，以及跨层的衔接：写盘与内存各存一份状态、缓存与真值、追加与重放。这类缺口在套件里常按层各管一头，镜像里一个真实对象一步就露出来。

纯函数逻辑不进镜像，在干净进程里载入系统加断言更快。

## 先确认镜像的版本

镜像早于本轮源码时，验的是旧代码。载入前先探测本轮新增的符号、槽或变量是否存在，不存在就先载入。载入顺序决定宏与内联函数的生效版本。

## 系统名可能解析到另一份副本

`asdf:load-system` 按注册表解析系统名。同一系统在源码注册表（依赖缓存、上一份克隆）里也有一份时，载入与判据跑的是那份副本，本轮改的文件不参与编译，读数拿旧代码给出。

- 载入前读一次 `(asdf:system-source-directory (asdf:find-system :system))`，与工作树路径比对。不一致就是副本。
- 改用自己的副本：把源注册表指到该工作树，再清掉系统缓存，三步按序。
  1. `(asdf:initialize-source-registry '(:source-registry (:directory <root>) (:tree <root>) :inherit-configuration))`
  2. `(asdf:clear-system :system)`；未导出时用 `(funcall (find-symbol "CLEAR-SYSTEM" "ASDF") :system)`
  3. `(asdf:load-system :system :force t)`
- 只 `asdf:load-asd` 工作树的 asd 不够：注册表里已登记的副本仍然胜出，载入的仍是副本。实测两次载入的来源路径都指向副本。
- 判据：`(sb-introspect:definition-source-pathname (sb-introspect:find-definition-source #'fn))` 落在本轮工作树内。`system-source-directory` 与编译输出文本都可能指向副本，不能单独当判据。

## worker 堆里没有当前上下文

独立 worker 是新进程，进程级的当前上下文没有绑定：当前配置、当前会话一律为 NIL。读这些上下文的代码在 worker 里报的是参数为 NIL，不是行为错误。

- 报错形如 `The value NIL is not of type SETINKA:CONFIGURATION`。见到「值为 NIL，类型是某个上下文」，先判这个上下文在 worker 里有没有绑定，再判代码逻辑。
- 要读配置的链，把 configuration 当参数显式传进来，不依赖进程级的当前值。
- 判据：worker 里的红项分「上下文缺失」与「行为不对」两类，前者换入口重跑，后者才改代码。

## 钩子装在跑那条链的进程里

观测一条链的行为，钩子必须装在它实际运行的进程里。入口跑在活动镜像、钩子装在 `lisp.eval` worker 里时，钩子一次也不会命中：日志为空，看起来像「没有调用经过这里」。

- 判据：钩子装好后触发一次入口，日志计数从 0 变成非 0。仍为 0 就换进程，不加更多钩子。
- 探针与被观测的链同一进程时，探针覆盖的定义在文件重载后消失。复查 `(sb-kernel:%fun-name (symbol-function #'fn))` 回到原名符号，说明探针已不在。

## 线程不继承这一轮的绑定

在 `let` 里绑定特殊变量只影响当前线程。入口或测试自己 spawn 线程时，那些线程读到的是全局值，本轮绑定对它们无效。

- 判据：红项集中在「请求去了意外的地址」或「读到默认值」这类症状上，而同一入口单线程地跑是绿的，先查绑定是不是只落在调用线程。
- 置值前先问这个变量会不会被别的线程读。会则用 `setf` 改全局值，用完还原；只在确实单线程的路径上用 `let`。
- 把 `let` 换成 `setf` 后红项全绿，说明缺的是全局值，不是代码逻辑，不必改被测代码。

## 删掉的定义要手工撤掉

载入新文件只增加定义，不删除定义。源码里删掉的方法仍挂在泛函上，删掉的函数仍可调用，它们继续按旧行为改写状态，把本轮验证抵消掉。

1. 载入本轮改过的文件。
2. 列出泛函方法：`(sb-mop:generic-function-methods #'gf)`，按限定词与特化器认出源码里已不存在的方法，用 `(find-method #'gf '(:after) (list ...) nil)` 取到后 `remove-method` 摘掉。
3. 对源码里已不存在的函数调用 `(fmakunbound 'name)`。
4. 复查：`(fboundp 'name)` 为 `NIL`，泛函方法表只剩源码里仍有的方法。

签名变更后 `load` 会报 `STYLE-WARNING ... does not match the old FTYPE proclamation`，这是重定义时的正常提示，不是失败。

## 伪造输入验证路径

在替身对象上塞入伪造值，跑真实入口，读它走了哪条分支。

- 对象用 `make-instance` 造，落盘路径指向 `/tmp`，`persisted-p` 为 `NIL`，用完删除文件。
- 伪造值先单独过对象自己的校验谓词（`...-p`），校验为真再往下走；不合法时读者一侧直接拒绝，读数全是 `NIL`，看起来像实现错误。
- 一次调用只收一个读数，多个读数合成 plist 返回；会抛错的步骤各自 `handler-case` 包住，一处失败不掩盖其余读数。
- 反事实取自 git 原文：`git show origin/master:path` 里被删掉的那段，说明同一输入在旧代码下走另一条分支。读数与原文并列才算证明，单看新代码只是自证。

样本类改动的例子：伪造一个通过校验的 sample 挂到临时会话上，调用旧代码会作废的那条入口，读 sample 是否仍是原值。

## 镜像不对应任何提交

镜像里的状态与提交对不上，事后无法重现那次验证。验证完丢弃即可；需要长期保留的改动走项目自己的落盘路径。
